# Практика 1. Нормализация событий и первичное расследование

Клиника, неделя 10–16 марта 2025. Жалоба: «с портала, похоже, утекли данные пациентов».
Есть выгрузка трёх журналов: входы, веб-портал, серверы. SIEM нет.

## Порядок работы

0. Развернуть Elasticsearch + Kibana и загрузить журналы — **[deploy.md](deploy.md)**
1. Оценить журналы как источники
2. Нормализовать журналы в ECS — **[ecs-reference.md](ecs-reference.md)**
3. Расследовать атаку
4. Настроить правило обнаружения
5. Написать отчёт смены

## Часть 1. Журналы как источники

Discover → «Сырые журналы (raw-\*)». Щелчок по названию поля слева — самые частые значения.

1. Что означает каждое поле каждого журнала? Что в значениях необычного?
2. На что отвечает каждый журнал: **кто**, **откуда**, **куда**, **что сделал**, **чем кончилось**? Чего не хватает, что потребовать у владельцев систем?
3. Лицензия SIEM ограничена по объёму. Какие 5 типов событий (`event_type`) подключить первыми, какие 3 — не подключать?

## Часть 2. Нормализация

Для каждого поля сырого журнала — поле ECS с тем же смыслом (`ecs-reference.md`).

1. Образец: Ingest Pipelines → `norm-web`.
2. Конвейер `norm-auth` для журнала входов (вместе с преподавателем): создать, проверить в **Test pipeline**, пропустить журнал. Console:
   ```
   POST _reindex?refresh=true
   { "source": { "index": "raw-auth" }, "dest": { "index": "norm-auth", "pipeline": "norm-auth" } }
   ```
3. Конвейер `norm-system` для журнала серверов — самостоятельно; затем `_reindex` из `raw-system` в `norm-system`.
   - Что означает `source_ip` в этом журнале? Сравните с `hostname`.
   - Поля `from_ip`, `process`, `command` есть не у всех событий.
   - Проверьте конвейер на событии с `from_ip : 198.51.100.45` до сохранения.
4. Проверка: Discover → «Нормализованные журналы (norm-\*)» → `source.ip : 198.51.100.45` → поле `event.dataset`: должны быть все три журнала.

## Часть 3. Расследование

Discover → «Нормализованные журналы (norm-\*)».

1. Кто выделяется среди неудачных входов? Все ли внешние адреса — атакующие?
2. Какие учётки подобраны, какими инструментами сканировали портал, какие уязвимости пробовали?
3. На какие серверы попали, что запускали, как закрепились?
4. Этапы атаки по MITRE ATT&CK: этап — что видно — журнал.
5. Можно ли утверждать, что данные пациентов утекли? Чего не хватает?

## Часть 4. Правило обнаружения

Detection rules → Create new rule → **Threshold**: `event.action : "login_failed"`, группировка по `source.ip`. Проверка — **Rule preview** (включать правило не нужно).

1. Сработает ли «5 неудач за 5 минут»? Почему?
2. Порог и окно, при которых ловятся атакующие и не ловятся сотрудники.

## Часть 5. Отчёт смены

10–15 строк руководителю: что произошло; что затронуто; что сделать неотложно; что настроить, чтобы видеть вовремя; чего пока не знаем.
